babyg should be usable for every creator, on every device, with every assistive technology. we're not there yet. this page describes what we work toward and how to tell us when we miss.

our commitment

we aim to make babyg conform to the web content accessibility guidelines (WCAG) 2.1 level AA as a baseline. this is an ongoing effort, not a finished claim, and we treat accessibility bugs the same way we treat any other production bug.

mobile-first design

babyg is built mobile-first. specifically:

  • form inputs use a 16px minimum font size so mobile safari doesn't zoom and lose context on focus.
  • safe-area insets are respected on iphone notch and home-indicator devices.
  • tap targets follow a minimum 44×44 px guidance where practical.
  • color contrast is checked against the babyg dark palette during design review.

keyboard and screen reader goals

we work to make every interactive element reachable by keyboard alone, and every meaningful image, button, or icon labeled for screen readers.

  • semantic HTML for headings, lists, forms, and landmarks.
  • visible focus states on all keyboard-focusable elements.
  • aria-label on icon-only buttons and avatars.
  • form fields with associated <label> elements.

we know there are gaps. some pages still rely on motion or visual cues that aren't yet announced to screen readers. fixing those is on the roadmap.

motion and animation

the landing page uses subtle scroll-reveal and parallax. these honor prefers-reduced-motion in most places, and we're working to add it everywhere it's missing.

ongoing improvements

we audit accessibility periodically and treat findings as bugs to be fixed in the next release. when a report comes in, we triage it on the same schedule as any other production issue.

report an issue

if you hit an accessibility barrier — a button you can't reach with a keyboard, an unlabeled icon, a contrast problem, a screen-reader misread — please tell us:

  • email {{ contact_email }}
  • include the page url, the device and browser you're using, and a short description of what didn't work.
  • if you use a screen reader, please tell us which one and which version.

response process

we aim to acknowledge accessibility reports within two business days and tell you whether a fix is in the next release or further out. urgent issues (something that fully blocks access) get triaged immediately.

what this statement is not

this is not a claim of full compliance with any specific standard. we aim toward WCAG 2.1 AA but have not been audited by a third party. the words "we aim to" and "we work to" are deliberate. they describe an ongoing commitment, not a finished state.
